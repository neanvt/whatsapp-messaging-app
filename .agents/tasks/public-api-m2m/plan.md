# Implementation Plan — Public server-to-server (M2M) API with per-tenant API keys

Derived from `design.md` (iteration 3) and `requirements.md`. Every item is grounded in the real codebase (verified files: `src/app/api/messages/send/route.ts`, `src/lib/whatsapp.ts`, `src/lib/crypto.ts`, `src/lib/auth.ts`, `src/lib/db.ts`, `prisma/schema.prisma`, `scripts/add-tenant-meta-app-table.mjs`, `src/components/dashboard/sidebar.tsx`, `src/app/docs/page.tsx`, `src/app/dashboard/settings/page.tsx`).

Stack is locked: Next.js 14 App Router, TypeScript, Prisma 5.x + libSQL/Turso adapter, zod, Tailwind + `@/components/ui/*` (badge, button, card, input, label all exist), Node `crypto`. No new dependencies. DB changes ship via an idempotent `@libsql/client` script, never `prisma db push`. Build command is `npm run build` (`prisma generate && next build`); lint is `npm run lint`.

Order is by dependency: schema/pure-helpers first, then the auth helper + send extraction + public routes, then management routes + UI + docs + scratchpad, then the full verification pass and commit.

- [ ] 1. Add the `ApiKey` Prisma model to `prisma/schema.prisma`.
      Add the model exactly per design §1.1: `id @default(cuid())`, `userId` + `user User @relation(onDelete: Cascade)`, `whatsappNumberId` + `whatsappNumber WhatsAppNumber @relation(onDelete: Cascade)`, `name String?`, `keyPrefix String`, `keyHash String @unique`, `lastUsedAt DateTime?`, `revokedAt DateTime?`, `createdAt @default(now())`, `updatedAt @updatedAt`, `@@index([userId])`. Do NOT add a redundant `@@index([keyHash])` (the `@unique` already produces the lookup index). Add inverse relation fields: `apiKeys ApiKey[]` on `User` and on `WhatsAppNumber`.
      Files: `prisma/schema.prisma`
      Verify: `npx prisma generate` succeeds and the generated client types include `ApiKey` with a unique `keyHash` (also validated by `npm run build` in step 11).

- [ ] 2. Create the idempotent libSQL migration script `scripts/add-api-key-table.mjs`.
      Clone the mechanics of `scripts/add-tenant-meta-app-table.mjs` byte-for-byte: manual `.env` parse, `createClient({ url: env.TURSO_DATABASE_URL, authToken: env.TURSO_AUTH_TOKEN })`, one `PRAGMA table_info(ApiKey)` probe used ONLY for the log line, then run all three DDL statements unconditionally (each `IF NOT EXISTS`): `CREATE TABLE IF NOT EXISTS ApiKey (id TEXT PRIMARY KEY NOT NULL, userId TEXT NOT NULL, whatsappNumberId TEXT NOT NULL, name TEXT, keyPrefix TEXT NOT NULL, keyHash TEXT NOT NULL, lastUsedAt TEXT, revokedAt TEXT, createdAt TEXT NOT NULL, updatedAt TEXT NOT NULL)`, `CREATE UNIQUE INDEX IF NOT EXISTS ApiKey_keyHash_key ON ApiKey (keyHash)`, `CREATE INDEX IF NOT EXISTS ApiKey_userId_idx ON ApiKey (userId)`. No FOREIGN KEY, no SQL timestamp defaults. `catch → console.error(non-secret) → process.exit(1)`, `client.close()` in `finally`.
      Files: `scripts/add-api-key-table.mjs`
      Verify: `node scripts/add-api-key-table.mjs` exits 0 and logs "ApiKey table created."; run it a SECOND time — exits 0, logs "ApiKey table already exists. Skipping.", no error, no duplicate (AC1). Then confirm against live Turso that table `ApiKey` and indexes `ApiKey_keyHash_key` + `ApiKey_userId_idx` exist (query `PRAGMA table_info(ApiKey)` and `PRAGMA index_list(ApiKey)` via a throwaway `@libsql/client` snippet or the Turso CLI; delete the throwaway after).

- [ ] 3. Create pure key helpers in `src/lib/api-key.ts` (no DB, no request).
      Implement per design §2 and §4.4: `generateApiKey()` → `{ plaintext, hash, prefix }` using `crypto.randomBytes(32).toString("base64url")`, `plaintext = "wa_live_" + random`, `prefix = "wa_live_" + random.slice(0,4)`; `hashKey(plaintext)` → SHA-256 hex; `looksLikeApiKey(token)` → starts with `wa_live_` and `length >= "wa_live_".length + 43`; `isSuperAdminUser({ email, role })` → `email === (process.env.SUPERADMIN_EMAIL || "neanvtech@gmail.com") || role === "superadmin"` (both params typed `string`). Never log plaintext/hash/random bytes.
      Files: `src/lib/api-key.ts`
      Verify: `npm run build` (step 11) type-checks the module; a quick `node -e`/REPL sanity check that `hashKey(generateApiKey().plaintext) === generateApiKey-returned hash` for a single call and that `looksLikeApiKey` accepts a generated key and rejects `"bad"` and `"wa_live_"` (remove any throwaway after).

- [ ] 4. Create the API-key auth helper in `src/lib/api-auth.ts`.
      Implement per design §3: `ApiKeyContext { userId, apiKey, number }`; `authenticateApiKey(request)` parses `^Bearer\s+(.+)$`, trims, `looksLikeApiKey` shape-gates (return `null` with no DB hit), `hashKey`, `prisma.apiKey.findUnique({ where: { keyHash } })`, return `null` if missing or `revokedAt` set, constant-time compare via `crypto.timingSafeEqual` on equal-length hex buffers, load bound `prisma.whatsAppNumber.findUnique({ where: { id: apiKey.whatsappNumberId } })` (null → `null`), fire-and-forget `lastUsedAt` update (`.catch(() => {})`, not awaited), return `{ userId, apiKey, number }`. Export `unauthorized()` → `NextResponse.json({ error: "Invalid or missing API key" }, { status: 401 })`. Never log the token or hash on any branch.
      Files: `src/lib/api-auth.ts`
      Verify: `npm run build` (step 11) type-checks; depends on step 1 (ApiKey client types) and step 3 (`hashKey`, `looksLikeApiKey`).

- [ ] 5. Extract the shared send core into `src/lib/send-template.ts`.
      Lift the body of `src/app/api/messages/send/route.ts` from AFTER its number/template/OTP/credits input validation into `sendTemplateMessage(input)` per design §4.1. Signature: `SendTemplateInput { userId, number, template, recipient, variables?, isSuperAdmin }` → `SendTemplateResult` discriminated union (`{ ok:true, message:{ id, status:"sent", metaMessageId } }` | `{ ok:false, code:number, error:string }`). The function owns, verbatim where possible: OTP guard (early `code:400` "OTP code variable required for authentication template"); credits check (non-superadmin, missing or `totalCredits <= 0` → `code:402` "Insufficient credits"); message create (`status:"queued"`); credit deduct; `resolveSendCredentials(number)` in try/catch → nulls; null-credential branch → `failed` + refund + `code:500` "WhatsApp number is not connected. Reconnect it to send messages."; Meta payload build incl. the `#131008` auth-template url-button keyed on `variables?.[0]`, `recipient.replace(/\D/g,"")`, `language.code ?? "en"`; `fetch https://graph.facebook.com/v19.0/{phoneNumberId}/messages`; capture `metaData.messages?.[0]?.id`; message update; refund-on-failure using the SAME `isSuperAdmin` boolean; Meta non-2xx → `code:500`. Keep the existing `console.log`/`console.warn`/`console.error` lines unchanged (no secrets). The helper returns a plain object, never a `NextResponse`, and never reads a session. Credit code is `402` inside the helper (session wrapper remaps to 400 in step 6).
      Files: `src/lib/send-template.ts`
      Verify: `npm run build` (step 11) type-checks; behavioral parity is proven in step 12.

- [ ] 6. Rewrite `src/app/api/messages/send/route.ts` as a thin session wrapper over `sendTemplateMessage`.
      Per design §4.3: keep the session 401, the four-field 400 ("Missing required fields"), the number `findFirst` (owned + `verificationStatus:"verified"`) 400 "Invalid or unverified WhatsApp number", the template `findFirst` (owned + `status:"approved"`) 400 "Template not found or not approved"; then call `sendTemplateMessage({ userId: session.user.id, number, template, recipient, variables, isSuperAdmin: session.user.role === "superadmin" })`; on `!result.ok` remap `result.code === 402 ? 400 : result.code` and return `{ error: result.error }`; on success return `{ id: result.message.id, status: "sent", message: "Message sent successfully" }`; keep the top-level try/catch → 500 "Internal server error". The externally observable behavior (status codes, messages, body, ordering: OTP-400 before credits-400 before any side effect) must be identical to the pre-refactor route.
      Files: `src/app/api/messages/send/route.ts`
      Verify: `npm run build` (step 11); step 12 does a static trace confirming every pre-refactor observable (codes, strings, success body) is preserved, including the deliberate `402→400` remap (NFR6/AC15).

- [ ] 7. Create the public send route `POST /api/v1/messages`.
      Per design §5.1: `const ctx = await authenticateApiKey(request); if (!ctx) return unauthorized();`. zod body `{ recipient: z.string().min(1), templateName?: z.string().min(1), templateId?: z.string().min(1), variables?: z.array(z.string()) }` with `.refine(b => !!b.templateName !== !!b.templateId, "Provide exactly one of templateName or templateId")` → 400 on failure. Ignore any client number field; always use `ctx.number`. Resolve template `prisma.template.findFirst({ where: { userId: ctx.userId, status:"approved", ...(templateId ? { id: templateId } : { name: templateName }) } })`; if a row exists for owner+name/id but is not approved → 400, if no row at all → 404 (per edge-case list). Load owner `prisma.user.findUnique({ where: { id: ctx.userId }, select: { email: true, role: true } })`, compute `isSuperAdmin = isSuperAdminUser(owner)` ONCE. Call `sendTemplateMessage({...})`; map `ok:true` → `200 { id, status, metaMessageId }`; `ok:false` → `{ error }` with the helper's `code` verbatim (402/400/500). Wrap in try/catch → 500 "Internal server error". Never log the key.
      Files: `src/app/api/v1/messages/route.ts`
      Verify: `npm run build` (step 11); static trace in step 12 covers happy path, OTP-400, insufficient-credits-402, Meta-fail-500+refund, superadmin exemption, bound-number isolation.

- [ ] 8. Create the public message-status route `GET /api/v1/messages/[id]` and the public templates route `GET /api/v1/templates`.
      Per design §5.2: status route authenticates via `authenticateApiKey`/`unauthorized()`, then `prisma.message.findFirst({ where: { id: params.id, userId: ctx.userId, whatsappNumberId: ctx.number.id }, select: { id, status, recipientPhone, metaMessageId, errorMessage, sentAt, deliveredAt, readAt, createdAt } })`; no match → identical `404 { error: "Not found" }` (no existence oracle); never log the path id; return the selected projection (no credential). Per design §5.3: templates route authenticates the same way, reads optional `?status`, validates it against `["draft","pending","submitted","approved","rejected"]` (unknown → 400), `prisma.template.findMany({ where: { userId: ctx.userId, ...(status ? { status } : {}) }, select: { id, name, category, language, status }, orderBy: { createdAt: "desc" } })`. No number filter. Both are additive new files.
      Files: `src/app/api/v1/messages/[id]/route.ts`, `src/app/api/v1/templates/route.ts`
      Verify: `npm run build` (step 11); step 12 static trace confirms 404-no-oracle scoping and the status allow-list.

## Notes / assumptions

- `src/lib/api-key.ts` (pure) and `src/lib/api-auth.ts` (DB + request) are split per the design; this satisfies both the requirements' `src/lib/api-key.ts` and the task prompt's `src/lib/api-auth.ts`.
- The migration is applied ONLY via `scripts/add-api-key-table.mjs`; `prisma db push` is never run against live libSQL.
- No new dependencies: zod, Node `crypto`, Prisma, and the existing UI primitives suffice.
- Live-DB verification steps (steps 2, 12) require `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` in `.env`; if the live DB is unreachable in the execution environment, fall back to the static trace for lifecycle and state that explicitly, but the migration must still have been run against live Turso before commit.
