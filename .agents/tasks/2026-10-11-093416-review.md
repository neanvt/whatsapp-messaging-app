# Real Meta WhatsApp Cloud API multi-tenant onboarding

Replaces the fake number-onboarding flow (random 6-digit code, local `verified` flip, single global `META_*` fallback) with real Meta Cloud API onboarding over two paths — Embedded Signup (OAuth popup) and manual credential entry — storing a per-tenant AES-256-GCM-encrypted access token plus the real `wabaId`/`phoneNumberId` and Meta health fields. Both send paths are rewired to each number's own decrypted credentials, the existing webhook gains `X-Hub-Signature-256` verification and strict per-tenant inbound routing, and the detail UI surfaces the real `codeVerificationStatus`. The change spans 5 commits over `origin/main`, 25 files, +1870/-604, and the full regression gate (`npm run build`, crypto harness) passes.

Watch for: (confirmed) schema was applied to live Turso via a standalone `@libsql/client` script rather than `npm run db:push`, because the Prisma 5.22 CLI rejects the `libsql://` datasource — a documented, repo-consistent deviation from AC #2's stated mechanism, with all 8 columns verified live. (confirmed) every live Meta round-trip (OAuth code exchange, token validation, FB popup, health refresh, real delivery) is correctly recorded as needs-runtime-verification and was not claimed working from code.

**Verdict**: APPROVED

## High-level view

The two onboarding routes are validate-before-persist and atomic: Embedded Signup exchanges the OAuth code (no `redirect_uri`), resolves the WABA defensively (client value first, then `debug_token` granular scopes, else terminal 400), discovers the phone, fetches health, best-effort subscribes/registers (both non-fatal, register matched on numeric `133016` not message text), then encrypts and persists; the manual route validates the token live against Meta and does a three-way WABA tie-check where only a successful list that omits the phone is fatal. Nothing is written until all remote checks pass, and every response goes through `serializeNumber`, so neither plaintext nor ciphertext ever leaves the server.

Persistence uses an explicit find-then-branch (`upsertNumberForUser`), not a Prisma `upsert`, so a cross-tenant collision — including the create-race `P2002` — becomes a 409 rather than silently overwriting another tenant's row. This is the backbone of the multi-tenant isolation contract.

The crypto helper is textbook AES-256-GCM with a lazy, fail-loud 32-byte key check and a self-describing `iv.tag.ciphertext` format; the standalone `.mjs` harness proves round-trip, tamper-throws, and bad-key-throws and exits green.

The webhook reads the raw body before parsing, rejects with 401 when `META_APP_SECRET` is unset (closing the "handshake passes, nothing delivered" trap), enforces the `sha256=` prefix and a length guard before `timingSafeEqual`, and routes inbound messages strictly by `phone_number_id` with no env/"any verified" fallback — unmatched payloads are logged and skipped. Post-signature processing errors still return 200.

Both send paths preserve all prior behavior: the auth-template OTP guard still precedes the message row and credit deduction, the `#131008` URL-button component is still appended, credit deduct/refund and the superadmin exemption are intact, and a decrypt/config throw is funneled into the existing failed+refund branch so a token row is never left stuck at `queued`.

Docs are complete: `.env.example` drops Postgres `DATABASE_URL`, adds the Turso + full Meta set + `NEXT_PUBLIC_*` + `ENCRYPTION_KEY` by name only with the Meta-side prerequisites, and `scratchpad.md` carries the new endpoints, schema, env, webhook, and a dated change-log entry.

### Validate-before-persist onboarding, atomic across both paths

Both `embedded-signup` and `manual` perform every Meta round-trip before touching the DB (confirmed). Embedded Signup exchanges the code without `redirect_uri`, computes `tokenExpiresAt` from `expires_in` (null when absent), resolves `wabaId` from the client value first and otherwise reads `debug_token`'s `granular_scopes` defensively (`?? []`, numeric `target_ids?.[0]`), and terminates with a 400 when neither yields a WABA. The health fetch is the authoritative reachability gate (non-OK → 400, nothing saved), and the `display_phone_number` empty-key guard returns 400 before any write so the non-null `@unique` column is never fed an empty string. Registration is advisory: success, already-registered (`regData.error.code === 133016`, numeric not message text), and any other failure all proceed to persist (confirmed).

The manual route (confirmed) validates the provided token with `GET /{phoneNumberId}?fields=...` (non-OK → 400 with Meta's verbatim message, nothing saved), then branches the WABA tie-check exactly three ways: list OK + phone present → proceed; list OK + phone absent → fatal 400; list call failed → non-fatal warn with step-1 remaining authoritative. Only the provable mismatch is fatal, which is the correct data-integrity posture.

### Cross-tenant isolation via find-then-branch, not Prisma upsert

`upsertNumberForUser` (confirmed) does `findUnique` on the globally-unique `phoneNumber`, throws `NumberOwnedByOtherTenantError` when the row belongs to another `userId`, updates in place by `id` for the same user, and wraps the create in a `P2002` catch that rethrows the same error for the create race. Both routes map it to 409. Because `phoneNumber` is unique across all tenants with no compound key, this is the only correct shape — a Prisma `upsert` keyed on `phoneNumber` would silently overwrite another tenant's row. The inbound webhook mirrors this by writing only under the matched row's real `userId`.

### Webhook authenticity and strict routing

The POST handler reads `await request.text()` before parsing so the HMAC covers Meta's exact bytes (confirmed). The ordered gate — unset `META_APP_SECRET` → 401 + error log naming the key; missing/`!sha256=` prefix → 401; length-equality check before `timingSafeEqual`; mismatch → 401 — fails closed on every branch, and the app-secret-missing 401 deliberately closes the trap where a passing GET handshake masks a silently-401ing POST. Inbound resolution is strictly by `phone_number_id`; no match is logged and skipped with nothing written, and the old env / "any verified number" fallbacks are gone. Status mapping (`sent/delivered/read/failed` → `status`/`deliveredAt`/`readAt`/`errorMessage` by `metaMessageId`) is preserved, and post-signature processing errors still return 200.

### Send-path rewire preserves credits and OTP ordering

In `messages/send` (confirmed) the OTP guard (`category === "authentication" && !variables?.[0]` → 400) still runs before `message.create` and the credit deduction; the `#131008` button (`type: button`, `sub_type: url`, `index: "0"`) is still appended, now keyed on `variables?.[0]` to match the guard (the cosmetic alignment from the final commit, behavior unchanged); deduct-on-send / refund-on-failure and the superadmin exemption are intact; and the credential resolution is wrapped so a decrypt/config throw leaves both creds null, funneling into the existing failed+refund branch rather than a stuck `queued` row or a swallowed 500. `chat/[contactPhone]/send` applies the same wrap so the existing missing-creds 500 fires before `message.create` (the pre-existing `conversation.upsert`-before-guard ordering is unchanged by this PR and out of scope).

### Fake flow removed

`verify` is repurposed to a real health refresh (no random code; legacy no-token rows get a 400 "Reconnect" and never touch `verificationStatus`), `confirm` returns 410 behind the auth guard and can never mark a number verified, bare `POST /api/numbers` returns 400 directing to the two real paths, and the `[id]/verify` page is a pure redirect to the detail page (confirmed). The only remaining `Math.random` is the advisory registration PIN, not a verification code.
